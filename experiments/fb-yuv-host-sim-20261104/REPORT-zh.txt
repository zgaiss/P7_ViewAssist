Framebuffer 自有 YUV 槽：独立主机仿真结果
2026-11-04

已完成实际字节复制模块、换帧/退休模型、错误与崩溃注入、重启日志
及精确恢复验收。最终 34 个场景均符合预期，包括故意构造的反例。
这没有证明目标驱动安全：真实路径仍停用，退休、cache、排空和
原分配恢复的真实契约仍缺失，最后 keeper 崩溃问题也没有解决。

1. 工作范围与复现

全部新增工作位于：
  experiments/fb-yuv-host-sim-20261104

没有接入真实 IPU、framebuffer、车辆、原应用或目标动态库；没有
网络访问、部署、设备 ioctl、真实 mmap、修改显示状态或安全设置。
模型代码只使用 Python 标准库和此目录内的模块、结果及日志文件。
十六进制地址仅用于模拟身份比较，未用作真实内存映射或写入地址。

运行：
  python3 -B run_suite.py results-reproduce
  python3 -B verify_results.py results-reproduce
输出目录须不存在；所有输出都留在这个独立目录之下。
最终验收目录是 results-verified；不将早期开发运行重复计数。

2. 实际 YUV 复制：39 组组合、5,751,162 个分量样本

layouts.py 真正构造和复制 bytearray，独立像素取样与已知测试图样
逐分量比较，不只测试状态布尔量。覆盖 I420、YV12、NV12 三种目标
布局、三个槽位、额外 framebuffer 行 padding、VPU 行/高度 padding、
非零偶数裁剪及 1280×720。验证其他槽、尾部 guard、源帧和 padding
未被误写，YV12 平面顺序与 NV12 交错也逐分量核对。

具体布局反例：
  源 320×180、stride320，VPU allocation height=192；
  源 U/V offset=61440/76800，FB 紧凑 I420=57600/72000。
  简单按 FB 总字节数复制连续源内存，会把 Y padding 当作 U 数据。
  反例测试明确捕获首个 U 分量错误。
  正确模块按各平面的 stride、裁剪和可见行数复制，可移除这类错位。

复制完成后将源数组清零并释放其模型租约，FB 自有副本不变。
这样可以在 CPU 复制完成后解除 VPU 源帧依赖；它仍不是零拷贝。
模块不缩放，不把不同宽高当作可接受输入。

10 类无效复制（已释放源、CPU可见性未知、奇数/越界裁剪、平面
重叠、源截断、尺寸不符、无效槽、目标短、地址不对齐）均在目标
变化前拒绝。560×315 等奇数4:2:0几何按保守模型规则拒绝；没有
据此声称目标驱动必然拒绝该尺寸。真实格式能力仍需独立取证。

3. 换帧与退休：四个时刻保持分开

模型分别记录：
  CPU 复制及 cache 交接；软件 pan 返回；新槽成为 current；
  旧槽最后一次读取结束并获得相应 epoch/版本的可信退休确认。

初始化 completion credit 可以让第一次 pan 返回，但不能证明任何
帧已显示或退休。软件 IRQ 只是通知，不自动改变任何帧的租约。
current 切到新槽后，模型允许旧槽仍有在途读取，直到独立事件确认。
这是为尚未被证据排除的行为保留空间，不是目标硬件的实测结论。

三个故意错误的重用规则分别产生逻辑重叠反例：
  - pan返回0 → 立即重用旧槽；
  - 收到一次可能过期/无关联IRQ → 重用旧槽；
  - current索引变化 → 重用旧槽。
独立设备观察器发现模拟硬件仍持有旧槽；guard 中止即将发生的
重写。没有真实 DMA、主机 UAF 或设备故障被执行。

严格模型在旧槽有可信退休确认后才重用，拒绝伪造、过期版本和
上一个 epoch 的确认；超时隔离之后的迟到确认或 IRQ 不自动恢复。
有限交错检查中，“可信确认且未隔离”规则遍历24个状态、42条边，
未见所定义的提前重用；另三种规则均找到短反例。范围仅是一旧一新
帧的有限布尔模型，不是完整内核或全部任务序列的安全证明。

4. 被吞掉错误：事后隔离仍可能晚于坏帧

模型依据已有静态证据注入 offset 更新错误不传播：软件 pan 返回0，
硬件仍可能使用错误的平面 offset。负例中坏帧先成为可见状态，
策略随后才隔离。这是本轮的重要限制：防止后续重用不能倒过来
保证第一帧不会错。没有真实错误传播/配置验收契约时必须拒绝启用。

select 错误被吞掉的场景也返回0，但新帧没有排入硬件队列；模型
保持源/槽不复用，等不到可信状态便隔离。显式地址更新失败、pan
等待超时、重复待提交造成的结果不确定也进入粘性隔离。

cache 单独建模：CPU 数组变化不自动同步给设备视图。缺少模型
cache 确认时，策略拒绝提交；故意绕过后能观察到陈旧帧负例。
模型 cache 确认只是测试 oracle，不是已有目标 cache API 的实现。

5. 异常与重启

worker、controller、最后 keeper 崩溃均通过模型事件注入；FakeDevice
继续持有读取状态，新的 Controller 对 DIRTY 日志保守进入
IRRECOVERABLE_UNCONFIRMED，不提交新帧，不把退出当作停止 DMA。
另将64字节真实写入主机槽数组后模拟复制中断，验证半帧从未获得
READY/cache/提交状态，重启也不发布它。

8种无效JSON/schema（含布尔版本号、零/负代次与不匹配的伪CLEAN）
均被拒绝；CLEAN但分配身份改变也停用。
模型在模式/槽写入前记录DIRTY，日志使用文件fsync及rename；没有
执行真实进程SIGKILL、断电、目录持久化或自主生产监护验证。
不能把这些重启模型称为 keeper 崩溃已安全。

6. 精确恢复：地址、长度、代次、矩阵均单独验收

恢复前先要求独立可信的“所有模拟DMA停止”确认。blank返回0或
cached blank=4 均不能代替它：注入底层未停止而上层仍成功时，模型
拒绝写回像素/模式，保留活动与待提交状态的不确定性。

恢复验收比较完整模型快照：几何、格式、stride、COM/GW/位置、
CSC矩阵签名、activate、blank/enable、整段
像素哈希、物理基址、分配长度、allocation和mapping代次。
实际硬件还有未建模寄存器，故这里的“完整”只针对模型字段。

扩容反例采用560×316 I420、三槽796320字节：
  原分配：base=0x18580000，length=460800，generation=1。
  模式恢复后：base=0x18a00000，length=796320，generation=2。
  几何、DP模型字段和原像素前缀都相等，精确恢复仍明确失败，
  差异含 base、length、allocation/mapping代次及整段像素哈希。
  日志标为RESTORE_MISMATCH，不写CLEAN，不猜测向原物理地址写回。

默认策略现已提前拒绝确定需要更大分配的候选，未改模式或像素，
也不写DIRTY；上述扩容只在明确的负例开关中放行。能在旧长度中
放下也不证明真实内核不会重分配；运行时身份变化仍会触发停用。

矩阵残留和强制activate变化分别有独立恢复失败用例，不能通过
只比较几何、像素和COM来隐藏。只有在无扩容、收到可信FakeDevice
全局停止、并明确恢复矩阵等模型状态的正面控制中，才得到
RESTORED_EXACT。这个测试前提在真实目标上尚未具备。

7. 最终结果与边界

results-verified/summary.json：34个场景通过、0个非预期失败，包含
6个显式负面控制；另外覆盖多类恢复不匹配与保守拒绝。
verify_results.py 独立重放386条事件，核对35次受保护复制与2次
模型退休接受，不把危险负例混入安全路径。测试源码快照与哈希一致。

仍明确为false：
  target_route_enabled
  target_sync_or_restore_contract_proven
  keeper_crash_safety_resolved

模型没有 OEM 并发生产者，没有真实 IPU/IDMAC/DP、行扫描、缓存或
中断实现，也没有屏幕上FG临时位置归零的物理时序。目标返回码、
任务与IRQ关联、错误发生后第一次可见画面、总线最后读取以及最终
文件/进程清理仍需匹配的驱动和硬件契约，不能由本测试补齐。

下一步可继续离线补齐这些契约与目标源码，核对错误传播和按帧退休
边界；在此之前只保留这个独立模型。没有连接或更改现有应用，
没有把任何“可信FakeDevice确认”伪装成可用的目标操作。
